# 变更记录与文档维护规范

## 1. 文档维护规范（每次改代码都要执行）

改完代码，在提交前按这四步更新文档。**这是整套文档能省 token 的前提**：文档一旦落后，下一个 AI 只能重新读源码，前面的功夫全废。

### 第一步：本篇加一条记录

在 §3 顶部按倒序加一条，格式：

```markdown
### YYYY-MM-DD 一句话标题

- 改了什么：具体到文件和函数
- 为什么：动机或修的什么问题
- 牵连：新增/改动的接口、字段、类名、配置
- 已更新文档：06 §2、04 §2
```

“牵连”那行最值钱，写清楚别人会被什么绊到。

### 第二步：按改动类型更新对应文档

| 改动类型 | 必须同步的文档 |
| --- | --- |
| 加/删/改文件 | [06-文件地图.md](06-文件地图.md) 的表格（作用、关键符号、行数） |
| 加/改接口 | [04-接口与数据字典.md](04-接口与数据字典.md) 的清单和字段 |
| 加/改设置项 | 04 的设置字段表 |
| 改数据库表结构 | 04 的数据字典；若影响 `messages` 表，检查 07 §3 提到的 `cleanupFailedAttempt` |
| 改流程、数据流、SSE 协议 | [02-架构与数据流.md](02-架构与数据流.md) |
| 改 Electron、IPC、注入脚本、打包 | [07-桌面端与打包.md](07-桌面端与打包.md) |
| 新踩到的坑 | [05-故障排查.md](05-故障排查.md)，坑够大就同时写进 [00-AI-上手索引.md](00-AI-上手索引.md) §3 |
| 新增一类常见改法 | [03-常见修改操作.md](03-常见修改操作.md) |
| 目录结构变了 | 06 §1 和根 `README.md` |

### 第三步：检查 00 的路由表

新增功能模块要在 [00-AI-上手索引.md](00-AI-上手索引.md) §2 加一行，否则下一个 AI 找不到入口，只能全库搜。

### 第四步：只改动过的地方，不要重写文档

文档是增量维护的。别因为“顺手整理”把整篇重写——那会丢掉前人踩坑记下的细节。行号偏移了顺手修一下就好。

### 写文档的取舍

- 写**为什么**和**牵连**，不写源码能直接看出来的东西。函数签名不用抄，加一句“它同时会清空 `active_leaf_id`”才有价值。
- 宁愿短。写不动就只写清楚“改了哪个文件的哪个函数、会牵连什么”，比空着强得多。
- 文档和代码矛盾时以代码为准，同时把文档改对。

## 2. 同步公开仓库（每次改完代码都要执行）

开发是在安装目录 `AI Chatbot/important resource/` 里做的，本仓库（`Documents/AI-Chatbot-public`）是它的公开副本，**不会自己更新**。改完代码、写完文档后：

1. 把改动过的源码从 `important resource/` 拷到本仓库对应路径（`origin resource/**`、`source/desktop/**`、`source/package.json`）。构建产物不要拷，`.gitignore` 已经挡掉 `source/frontend/`、`source/backend/`、`release/`、`electron-dist/`、`node_modules/`、`backend/data/`。
2. 版本号跟着 `source/package.json` 走，安装包本身不入库。
3. §1 的文档更新在本仓库这边做——本仓库的 `docs/00`、`06`、`07`、`08` 是这套文档的正本，开发目录那边没有。
4. `git status` 确认没有混进密钥、日志、用户数据，再提交。提交信息写清楚这次同步覆盖了哪几件事。

漏掉这步的后果不是冲突，而是公开仓库悄悄停留在旧版本——比如它曾经停在 1.2.3，而安装包已经发到 1.2.6。

### 2.1 发布顺序：先出包给用户测，**测过了才同步源码和提交**

这是用户定的节奏，别自作主张提前提交：

| 步骤 | 谁做 | 说明 |
| --- | --- | --- |
| 1. 改 `origin resource/` 源码 | AI | 前端改完构建并同步到 `source/frontend/`；**改了后端就重编 `chatbot-backend.exe`**（漏了不报错，见 05 §10.2） |
| 2. 更新文档 | AI | §1 的四步 |
| 3. 打包 | AI | 升 `source/package.json` 版本 → `npm run dist` → 报告产物路径 |
| 4. **停下来等** | — | **到这里就停**。不要同步公开库，不要 commit，不要 push |
| 5. 实测 | 用户 | 装包验证 bug 是否真的修好 |
| 6. 说「改源码提交」 | 用户 | 这句话是**放行口令** |
| 7. 同步公开库源码 | AI | 把 `origin resource/**`、`source/desktop/**`、`source/package.json` 拷到公开库副本，见 §2 |
| 8. 两个仓库都 commit + push | AI | 收到第 6 步口令即视为**已授权推送**，不必再问 |

要点：

- **「改源码」指的是同步公开库那份源码副本**，不是回头再改开发目录的代码。开发目录的代码在第 1 步就改完了、也是第 3 步打包的来源。
- 第 4 步的等待是刻意的。测出问题就回第 1 步接着改，**不会在仓库里留下一版没验证过的提交**。
- 第 8 步是这条流程里唯一免问推送的场景。用户没说那句口令时，`git push` 仍然要先问（私有库带明文 API key）。
- 发 Release 是独立的一步，用户可能自己在 GUI 里做掉。动手前先 `git fetch` 看看 tag 在不在，别重复发。

### 2026-08-25 1.2.14：拖动排序改用指针实现、新增启动画面、更新通道自动降级

三件事一起做，互相独立。

**① 拖动排序换实现，加上"缩小跟随 + 原位占位 + 相邻项让位"的视觉效果**

- 改了什么：
  - 新增 `../../origin resource/frontend/src/hooks/useSortableList.ts`，React 侧的指针拖动排序 hook。
  - `../source/desktop/page-enhancements.js` 新增 `makeSortable()`，替换掉原来多 API 卡片上的
    HTML5 drag&drop（`dragstart`/`dragover`/`drop` 三个监听器和手柄上那段 `card.draggable`
    临时开关全部删除）。自动滚动那套（1.2.13 加的）保留，只是触发事件从 `dragover`
    换成了 `pointermove`。
  - 输入框上方的模型菜单（`features/chat/components/Composer.tsx`）接上 `useSortableList`，
    顺序写回 `settings.models`。
  - 样式：`styles/shared-components.css` 加 `.sortable-ghost` / `.sortable-placeholder` /
    `.sortable-shifting` / `body.sortable-dragging`；`../source/desktop/enhancements.css`
    加同名但前缀为 `.enh-sort-` 的一套。
- 为什么：HTML5 drag&drop 的拖影是浏览器截的静态位图，改不了大小和透明度，也没法让下面的
  项目实时让位。要用户要的那套效果只能自己接指针事件。
- 牵连：
  - **两份实现要一起改**。React 的 hook 和注入脚本的 `makeSortable` 是等价逻辑，
    但注入脚本跑在 React 之外、只有 vanilla DOM，共用不了 hook。改动效果时别只改一处。
  - 中线判定用的是**进入拖动时快照的原始位置**（`baseTop`），不是实时的
    `getBoundingClientRect()`——后者已经被让位的 transform 改过了，拿它算会来回抖。
  - ghost 必须挂在 `document.body` 下：菜单和列表都可能有 overflow 裁剪，
    留在容器里拖出边界就看不见了。
  - 模型菜单的项既能点（选模型）又能拖，靠 `onClickCapture` 挡掉拖动结束后浏览器补的那次
    click，否则松手会顺带选中并关掉菜单。
  - `settings.models` 的顺序**只影响这个菜单怎么排**，和「多 API」列表的故障转移优先级
    是两回事。

**② 启动画面**

- 改了什么：新增 `../source/desktop/splash.cjs` 和 `splash.html`；`main.cjs` 的
  `app.whenReady()` 里在 `startBackend()` **之前**调 `splash.create()`，各步骤之间调
  `splash.setStatus()`，`createWindow()` 的 `ready-to-show` 里 `window.show()` 之后调
  `splash.close()`。
- 为什么：后端是 PyInstaller 单文件 exe，冷启动几十秒是常态，在它就绪之前主窗口还没创建，
  用户双击图标后屏幕上什么都没有，很容易以为没启动成功而反复双击。
- 牵连：
  - splash **不能走后端**（`loadFile` 一个本地 html），它必须在 `backendUrl` 存在之前就显示。
  - `splash.close()` 必须在 `window.show()` **之后**——反过来桌面会空一帧，看着像闪了一下。
  - 三处异常出口都加了 `splash.close()`：启动失败的 `catch`、后端意外退出的 `showErrorBox`
    之前。它是 `alwaysOnTop` 的，不收掉会压在对话框上面。
  - `waitForBackend()` 里超过 20 秒的那个分支顺带调 `setStatus` 补一句"首次启动需要解包"。

**③ 更新通道自动降级，检查时机改为只在启动时自动一次**

- 改了什么：
  - 新增 `../source/desktop/net-fallback.cjs`：`establish()` 依次尝试直连 → DoH 解析后直连
    → 镜像站 → HTTP 代理，返回第一个通的；`teardown()` 还原全部全局改动。
  - `updater.cjs`：`check()` / `download()` 前先 `openChannel()` 建通道并
    `setFeedURL({provider:'generic'})`，`finally` 里一定 `teardown()`。
    provider 从 github 换成 generic（github provider 会自己拼 `api.github.com`，
    镜像地址就用不上了）。新增 `state.channel` 字段告诉界面走的哪条线路。
  - 设置里新增「更新代理」输入框（`page-enhancements.js` 的注入设置区，
    存 `enhancements.updateProxy`）。
- 为什么：GitHub 在国内经常连不上，原来直连失败就放弃，界面上什么都不显示。
- 牵连：
  - **刻意不集成 Steamcommunity_302**。它靠 WinDivert 内核驱动做全局流量劫持、要管理员
    权限，应用没走到清理逻辑就退出（崩溃、直接关机）会把驱动和劫持规则留在系统里，
    下次开机整机网络异常。本模块的所有改动**只存在于当前进程内存**：不写 hosts、不装驱动、
    不改系统代理、不起子进程，进程一死就没了。这条**不要改**。
  - `teardown()` 记的是**被改过的那些 agent 对象本身**，不是"到时候再读一次
    `https.globalAgent`"——第 4 级会把 `globalAgent` 整个换掉，还原时再去读就读到代理
    Agent 了，`dohLookup` 会永久留在原 Agent 上影响后续所有请求。这个坑已经踩过一次。
  - `get()` 必须跟随重定向：`/releases/latest/download/xxx` 一定会 302 到
    `objects.githubusercontent.com`，不跟随的话探活永远只拿到一个 302。
    跟随时要清掉 `servername`（那是给按 IP 直连用的）。
  - DoH 服务器地址**必须写 IP 字面量**——这一级本来就是用来对付"域名解析不了"的。
  - 检查时机：启动后延迟 8 秒静默查一次（`autoCheckDone` 保证只有这一次），
    之后完全由界面上的「检查更新」按钮驱动，没有任何定时器。
- 已更新文档：08 §3、06 §2、07、04

### 2026-08-24 1.2.13：多 API 卡片拖动排序支持边缘自动滚动

- 改了什么：`../source/desktop/page-enhancements.js` 里多 API 卡片的拖动排序。
  新增一段自动滚动逻辑（`DRAG_SCROLL_ZONE` / `DRAG_SCROLL_MIN_SPEED` / `DRAG_SCROLL_MAX_SPEED`
  三个常量，`scrollableAncestor()`、`stepDragScroll()`、`updateDragScroll()`、
  `beginDragScroll()`、`stopDragScroll()` 五个函数），并在卡片的 `dragstart` 里调
  `beginDragScroll(list)`、在 `dragend` 和 `drop` 里调 `stopDragScroll()`。
- 为什么：API 数量多到超过设置弹窗一屏后，想把末尾的卡片拖到最前面做不到——
  原生 HTML5 拖放期间滚轮和滚动条都不响应，拖到列表边缘就卡住了。
- 牵连：
  - 触发区默认 60px，速度 2→18 px/帧线性递增（越贴边越快），用 `requestAnimationFrame` 驱动。
    要调手感改那三个常量即可，不用动逻辑。
  - `scrollableAncestor()` 是**运行时**从 `.enh-api-list` 往上找最近的可滚动祖先，
    实际命中的是设置弹窗的 `.modal-body`。以后若给 `.enh-api-list` 自己加上
    `overflow-y: auto`，滚动目标会变成它本身——行为仍然正确，但触发区会按列表高度的
    1/3 收窄（`zone` 那行的保护，防止上下触发区在矮容器里连成一片）。
  - `dragover` 监听挂在 **document 捕获阶段**而不是卡片上：指针滑出卡片、滑出列表时
    仍要能更新速度；且 drop 后 `renderApiList()` 会整体重绘，被拖的卡片已从 DOM 移除，
    它的 `dragend` 不保证触发，所以 `drop` 里也调了一次 `stopDragScroll()` 兜底。
  - 原有「按住 ⋮⋮ 手柄才临时 `card.draggable = true`、松手立即解除」的机制未改动
    （那是为了不劫持卡片内输入框的文本选中，见 05）。
- 已更新文档：07 §4（注入脚本）

- 牵连（**这些最容易绊人**）：
  - **每次发 Release 必须同时上传 `latest.yml`**，只传 exe 的话所有客户端都检测不到更新，
