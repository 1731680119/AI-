# 变更记录与文档维护规范

## 1. 文档维护规范（每次改代码都要执行）

改完代码，在提交前按这四步更新文档。**这是整套文档能省 token 的前提**：文档一旦落后，下一个 AI 只能重新读源码，前面的功夫全废。

### 第一步：本篇加一条记录

在 §3 顶部按倒序加一条，格式：

```markdown
### YYYY-MM-DD 一句话标题

- 改了什么：具体到文件和函数
- 为什么：动机或修的什么问题
- 牵连：新增/改动的接口、字段、类名、配置
- 已更新文档：06 §2、04 §2
```

“牵连”那行最值钱，写清楚别人会被什么绊到。

### 第二步：按改动类型更新对应文档

| 改动类型 | 必须同步的文档 |
| --- | --- |
| 加/删/改文件 | [06-文件地图.md](06-文件地图.md) 的表格（作用、关键符号、行数） |
| 加/改接口 | [04-接口与数据字典.md](04-接口与数据字典.md) 的清单和字段 |
| 加/改设置项 | 04 的设置字段表 |
| 改数据库表结构 | 04 的数据字典；若影响 `messages` 表，检查 07 §3 提到的 `cleanupFailedAttempt` |
| 改流程、数据流、SSE 协议 | [02-架构与数据流.md](02-架构与数据流.md) |
| 改 Electron、IPC、注入脚本、打包 | [07-桌面端与打包.md](07-桌面端与打包.md) |
| 新踩到的坑 | [05-故障排查.md](05-故障排查.md)，坑够大就同时写进 [00-AI-上手索引.md](00-AI-上手索引.md) §3 |
| 新增一类常见改法 | [03-常见修改操作.md](03-常见修改操作.md) |
| 目录结构变了 | 06 §1 和根 `README.md` |

### 第三步：检查 00 的路由表

新增功能模块要在 [00-AI-上手索引.md](00-AI-上手索引.md) §2 加一行，否则下一个 AI 找不到入口，只能全库搜。

### 第四步：只改动过的地方，不要重写文档

文档是增量维护的。别因为“顺手整理”把整篇重写——那会丢掉前人踩坑记下的细节。行号偏移了顺手修一下就好。

### 写文档的取舍

- 写**为什么**和**牵连**，不写源码能直接看出来的东西。函数签名不用抄，加一句“它同时会清空 `active_leaf_id`”才有价值。
- 宁愿短。写不动就只写清楚“改了哪个文件的哪个函数、会牵连什么”，比空着强得多。
- 文档和代码矛盾时以代码为准，同时把文档改对。

## 2. 同步公开仓库（每次改完代码都要执行）

开发是在安装目录 `AI Chatbot/important resource/` 里做的，本仓库（`Documents/AI-Chatbot-public`）是它的公开副本，**不会自己更新**。改完代码、写完文档后：

1. 把改动过的源码从 `important resource/` 拷到本仓库对应路径（`origin resource/**`、`source/desktop/**`、`source/package.json`）。构建产物不要拷，`.gitignore` 已经挡掉 `source/frontend/`、`source/backend/`、`release/`、`electron-dist/`、`node_modules/`、`backend/data/`。
2. 版本号跟着 `source/package.json` 走，安装包本身不入库。
3. §1 的文档更新在本仓库这边做——本仓库的 `docs/00`、`06`、`07`、`08` 是这套文档的正本，开发目录那边没有。
4. `git status` 确认没有混进密钥、日志、用户数据，再提交。提交信息写清楚这次同步覆盖了哪几件事。

漏掉这步的后果不是冲突，而是公开仓库悄悄停留在旧版本——比如它曾经停在 1.2.3，而安装包已经发到 1.2.6。

## 3. 变更记录

### 2026-08-14 修模型选择器不显示模型名、修桌面端启动超时（1.2.6 重打包）

- 改了什么：
  - `frontend/src/styles/shared-components.css` 给 `.model-picker-row label input` 加作用域覆盖（`width: auto !important` 等），压掉公共规则 `.field input:not([type='range']):not([type='radio']) { width: 100% }` 的影响。
  - `../source/desktop/main.cjs:waitForBackend:327` 不再是固定 30 秒超时：只要 `backendProcess` 还活着就继续等，硬上限 5 分钟；进程已退出则立刻失败，把真实死因让给 `exit` 回调；等待超过 20 秒写一条 warn 日志。
- 为什么：
  - 前者：那条公共规则排除了 range 和 radio 却没排除 checkbox，多选的「模型列表」里勾选框被撑成整行宽，把右边的模型名 `<span>` 挤成 0 宽——界面上只剩一个方框加「测试」按钮。搜索、图片那两处是单选（radio），所以不受影响。
  - 后者：崩溃记录里是 `startupFailed`／「等待本地后端启动超时」，正好卡在 30 秒，而 8 秒后手动重开就成功。后端是 PyInstaller 单文件 exe，刚升级后首次启动要解出几十 MB 并被 Defender 整包扫一遍，30 秒不够。
- 牵连：安装包版本仍是 **1.2.6**（覆盖重建，没有新号）。CSS 是作用域覆盖，不影响别处；`waitForBackend` 的失败文案变了，以后排查别再按「正好 30 秒」这个特征去找。
- 已更新文档：00 §0/§3、05 §2/§11、06 §2-3、07 §2、08

### 2026-08-13 模型检测：从上游清单里挑模型

- 改了什么：新增 `backend/model_probe.py`（`list_models:171` 读 `/models` 清单、`test_model:208` 对单个模型试调一次）；`routers/settings.py` 加 `POST /api/settings/model-list:136`、`POST /api/settings/model-test:144`；前端新增 `features/settings/components/ModelPicker.tsx`，`SettingsModal.tsx` 在聊天模型列表、每套搜索配置、图片模型三处加「检测可用模型」入口；`chatbot-backend.spec` 的 `hiddenimports` 补上 `model_probe`。
- 为什么：模型名以前只能手打，打错了要等发消息才报错；中转站上架几百个模型、名字还常带前缀，靠猜成本很高。
- 牵连：
  - 两个新接口**直接收 `base_url`/`api_key` 字段而不是读设置**，所以没保存也能测。
  - 桌面端的聊天地址和密钥由注入的「多 API」面板管理，`draft.base_url`/`draft.api_key` 是空的。因此上游抽象成 `ModelSource`，密钥用 `resolveKey()` 回调懒取（桌面端走 `chatbotDesktop.revealApiKey`）；**不要再用 `draft.base_url` 判断这类按钮该不该禁用**。
  - 判「路径不对、换下一个候选」的状态码分两套（`_PATH_MISMATCH_CODES` / `_CHAT_MISMATCH_CODES`），差别在 403，理由见 04 §2。
- 已更新文档：04 §2/§3、06 §2-3、README

### 2026-08-13 联网搜索支持多套配置

- 改了什么：`database.py` 把 `search_base_url` 等四个平铺字段合成 `search_providers` 列表 + `search_provider_id`，`get_settings` 里做旧字段自动迁移；`web_search.py` 加 `active_provider:78`、`normalize_provider:96`、`endpoint_candidates:156`、`test_provider:457`；`routers/settings.py` 加 `POST /api/settings/search-test:99`；设置页每套配置右上角带「检测」按钮。
- 为什么：官方直连和各家中转站要换着试，一套配置存不下；而且「填了但根本不通」以前只能靠发消息试出来。
- 牵连：读设置的代码不能再直接取 `settings["search_model"]`，要走 `web_search.active_provider(settings)`。调用失败**不会**自动切到别的配置——避免在用户不知情的情况下换一家继续花钱。
- 已更新文档：04 §2/§3、05 §11、06 §2
