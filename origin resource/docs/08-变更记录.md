# 变更记录与文档维护规范

## 1. 文档维护规范（每次改代码都要执行）

改完代码，在提交前按这四步更新文档。**这是整套文档能省 token 的前提**：文档一旦落后，下一个 AI 只能重新读源码，前面的功夫全废。

### 第一步：本篇加一条记录

在 §3 顶部按倒序加一条，格式：

```markdown
### YYYY-MM-DD 一句话标题

- 改了什么：具体到文件和函数
- 为什么：动机或修的什么问题
- 牵连：新增/改动的接口、字段、类名、配置
- 已更新文档：06 §2、04 §2
```

“牵连”那行最值钱，写清楚别人会被什么绊到。

### 第二步：按改动类型更新对应文档

| 改动类型 | 必须同步的文档 |
| --- | --- |
| 加/删/改文件 | [06-文件地图.md](06-文件地图.md) 的表格（作用、关键符号、行数） |
| 加/改接口 | [04-接口与数据字典.md](04-接口与数据字典.md) 的清单和字段 |
| 加/改设置项 | 04 的设置字段表 |
| 改数据库表结构 | 04 的数据字典；若影响 `messages` 表，检查 07 §3 提到的 `cleanupFailedAttempt` |
| 改流程、数据流、SSE 协议 | [02-架构与数据流.md](02-架构与数据流.md) |
| 改 Electron、IPC、注入脚本、打包 | [07-桌面端与打包.md](07-桌面端与打包.md) |
| 新踩到的坑 | [05-故障排查.md](05-故障排查.md)，坑够大就同时写进 [00-AI-上手索引.md](00-AI-上手索引.md) §3 |
| 新增一类常见改法 | [03-常见修改操作.md](03-常见修改操作.md) |
| 目录结构变了 | 06 §1 和根 `README.md` |

### 第三步：检查 00 的路由表

新增功能模块要在 [00-AI-上手索引.md](00-AI-上手索引.md) §2 加一行，否则下一个 AI 找不到入口，只能全库搜。

### 第四步：只改动过的地方，不要重写文档

文档是增量维护的。别因为“顺手整理”把整篇重写——那会丢掉前人踩坑记下的细节。行号偏移了顺手修一下就好。

### 写文档的取舍

- 写**为什么**和**牵连**，不写源码能直接看出来的东西。函数签名不用抄，加一句“它同时会清空 `active_leaf_id`”才有价值。
- 宁愿短。写不动就只写清楚“改了哪个文件的哪个函数、会牵连什么”，比空着强得多。
- 文档和代码矛盾时以代码为准，同时把文档改对。

## 2. 同步公开仓库（每次改完代码都要执行）

开发是在安装目录 `AI Chatbot/important resource/` 里做的，本仓库（`Documents/AI-Chatbot-public`）是它的公开副本，**不会自己更新**。改完代码、写完文档后：

1. 把改动过的源码从 `important resource/` 拷到本仓库对应路径（`origin resource/**`、`source/desktop/**`、`source/package.json`）。构建产物不要拷，`.gitignore` 已经挡掉 `source/frontend/`、`source/backend/`、`release/`、`electron-dist/`、`node_modules/`、`backend/data/`。
2. 版本号跟着 `source/package.json` 走，安装包本身不入库。
3. §1 的文档更新在本仓库这边做——本仓库的 `docs/00`、`06`、`07`、`08` 是这套文档的正本，开发目录那边没有。
4. `git status` 确认没有混进密钥、日志、用户数据，再提交。提交信息写清楚这次同步覆盖了哪几件事。

漏掉这步的后果不是冲突，而是公开仓库悄悄停留在旧版本——比如它曾经停在 1.2.3，而安装包已经发到 1.2.6。

### 2.1 发布顺序：先出包给用户测，**测过了才同步源码和提交**

这是用户定的节奏，别自作主张提前提交：

| 步骤 | 谁做 | 说明 |
| --- | --- | --- |
| 1. 改 `origin resource/` 源码 | AI | 前端改完构建并同步到 `source/frontend/`；**改了后端就重编 `chatbot-backend.exe`**（漏了不报错，见 05 §10.2） |
| 2. 更新文档 | AI | §1 的四步 |
| 3. 打包 | AI | 升 `source/package.json` 版本 → `npm run dist` → 报告产物路径 |
| 4. **停下来等** | — | **到这里就停**。不要同步公开库，不要 commit，不要 push |
| 5. 实测 | 用户 | 装包验证 bug 是否真的修好 |
| 6. 说「改源码提交」 | 用户 | 这句话是**放行口令** |
| 7. 同步公开库源码 | AI | 把 `origin resource/**`、`source/desktop/**`、`source/package.json` 拷到公开库副本，见 §2 |
| 8. 两个仓库都 commit + push | AI | 收到第 6 步口令即视为**已授权推送**，不必再问 |

要点：

- **「改源码」指的是同步公开库那份源码副本**，不是回头再改开发目录的代码。开发目录的代码在第 1 步就改完了、也是第 3 步打包的来源。
- 第 4 步的等待是刻意的。测出问题就回第 1 步接着改，**不会在仓库里留下一版没验证过的提交**。
- 第 8 步是这条流程里唯一免问推送的场景。用户没说那句口令时，`git push` 仍然要先问（私有库带明文 API key）。
- 发 Release 是独立的一步，用户可能自己在 GUI 里做掉。动手前先 `git fetch` 看看 tag 在不在，别重复发。

### 2026-08-19 修复图片编辑上传参考图无效（选完文件没反应也不报错）

- 改了什么：`../frontend/src/features/images/components/ImagePage.tsx` 的 `addRefs()`。原来把 `FileList` 直接传进 `setRefs` 的 updater，在里面才 `Array.from(files)`；改成在事件处理阶段就同步取出 `Array.from(files)`，并把 `setRefHint()` 和 `URL.createObjectURL()` 一并移出 updater。
- 为什么：`<input type="file">` 的 `onChange` 里紧接着执行了 `e.target.value = ''`（防止重复选同一文件时不触发 change），而 `input.files` 这个 `FileList` 是**活引用**——清空 value 后它同步变空。`setRefs` 的 updater 由 React 在事件处理函数结束后的批处理阶段才调用，那时 `Array.from(files)` 拿到的已经是空数组，于是参考图一张都加不进 `refs`。函数开头的 `files.length === 0` 早返回是同步执行的，那时还有内容，所以能通过——**这就是既没效果也没有任何报错的原因**。日志里两次 `POST /api/images/edit` 都是 `{"references": 0}`，证明请求根本没带参考图，不是后端拒收。
- 牵连：
  - **后端零改动。** `routers/images.py` 的 `/api/images/edit` 和 `images.py` 的 `edit_image_with_references()` 一直是好的，之前从没被真正触发过多图分支。
  - 主图上传不受影响：它走的是同步取值 `e.target.files?.[0]`，也没有清空 `value`。
  - 顺带修掉两个隐患：`setRefHint` 原先是在状态 updater 内做副作用（严格模式下会跑两次）；`URL.createObjectURL` 在 updater 内重复执行会泄漏 blob URL。
  - **同类模式要警惕**：`features/chat/components/Composer.tsx:223-225` 也是「onChange 里清空 value」，但它的 `handleFiles` 是同步消费 `FileList` 的，没有这个问题。以后再写这种 input，文件必须在事件阶段就拷成数组。
