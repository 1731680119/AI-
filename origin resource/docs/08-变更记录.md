# 变更记录与文档维护规范

## 1. 文档维护规范（每次改代码都要执行）

改完代码，在提交前按这四步更新文档。**这是整套文档能省 token 的前提**：文档一旦落后，下一个 AI 只能重新读源码，前面的功夫全废。

### 第一步：本篇加一条记录

在 §3 顶部按倒序加一条，格式：

```markdown
### YYYY-MM-DD 一句话标题

- 改了什么：具体到文件和函数
- 为什么：动机或修的什么问题
- 牵连：新增/改动的接口、字段、类名、配置
- 已更新文档：06 §2、04 §2
```

“牵连”那行最值钱，写清楚别人会被什么绊到。

### 第二步：按改动类型更新对应文档

| 改动类型 | 必须同步的文档 |
| --- | --- |
| 加/删/改文件 | [06-文件地图.md](06-文件地图.md) 的表格（作用、关键符号、行数） |
| 加/改接口 | [04-接口与数据字典.md](04-接口与数据字典.md) 的清单和字段 |
| 加/改设置项 | 04 的设置字段表 |
| 改数据库表结构 | 04 的数据字典 |
| 改流程、数据流、SSE 协议 | [02-架构与数据流.md](02-架构与数据流.md) |
| 改 Electron、IPC、注入脚本、打包 | [07-桌面端与打包.md](07-桌面端与打包.md) |
| 新踩到的坑 | [05-故障排查.md](05-故障排查.md)，坑够大就同时写进 [00-AI-上手索引.md](00-AI-上手索引.md) §3 |
| 新增一类常见改法 | [03-常见修改操作.md](03-常见修改操作.md) |
| 目录结构变了 | 06 §1 和根 `README.md` |

### 第三步：检查 00 的路由表

新增功能模块要在 [00-AI-上手索引.md](00-AI-上手索引.md) §2 加一行，否则下一个 AI 找不到入口，只能全库搜。

### 第四步：只改动过的地方，不要重写文档

文档是增量维护的。别因为“顺手整理”把整篇重写——那会丢掉前人踩坑记下的细节。行号偏移了顺手修一下就好。

### 写文档的取舍

- 写**为什么**和**牵连**，不写源码能直接看出来的东西。函数签名不用抄，加一句“它同时会清空 `active_leaf_id`”才有价值。
- 宁愿短。写不动就只写清楚“改了哪个文件的哪个函数、会牵连什么”，比空着强得多。
- 文档和代码矛盾时以代码为准，同时把文档改对。

## 2. 同步公开仓库（每次改完代码都要执行）

开发是在安装目录 `AI Chatbot/important resource/` 里做的，本仓库（`Documents/AI-Chatbot-public`）是它的公开副本，**不会自己更新**。改完代码、写完文档后：

1. 把改动过的源码从 `important resource/` 拷到本仓库对应路径（`origin resource/**`、`source/desktop/**`、`source/package.json`）。构建产物不要拷，`.gitignore` 已经挡掉 `source/frontend/`、`source/backend/`、`release/`、`electron-dist/`、`node_modules/`、`backend/data/`。
2. 版本号跟着 `source/package.json` 走，安装包本身不入库。
3. §1 的文档更新在本仓库这边做——本仓库的 `docs/00`、`06`、`07`、`08` 是这套文档的正本，开发目录那边没有。
4. `git status` 确认没有混进密钥、日志、用户数据，再提交。提交信息写清楚这次同步覆盖了哪几件事。

漏掉这步的后果不是冲突，而是公开仓库悄悄停留在旧版本——比如它曾经停在 1.2.3，而安装包已经发到 1.2.6。

### 2.1 发布顺序：先出包给用户测，**测过了才同步源码和提交**

这是用户定的节奏，别自作主张提前提交：

| 步骤 | 谁做 | 说明 |
| --- | --- | --- |
| 1. 改 `origin resource/` 源码 | AI | 前端改完构建并同步到 `source/frontend/`；**改了后端就重编 `chatbot-backend.exe`**（漏了不报错，见 05 §10.2） |
| 2. 更新文档 | AI | §1 的四步 |
| 3. 打包 | AI | **版本号不动**（见 §2.2）→ `npm run dist` → 报告产物路径 |
| 4. **停下来等** | — | **到这里就停**。不要同步公开库，不要 commit，不要 push |
| 5. 实测 | 用户 | 装包验证 bug 是否真的修好 |
| 6. 说「改源码提交」 | 用户 | 这句话是**放行口令** |
| 7. 升版本号并重新打包 | AI | 见 §2.2。这是唯一允许升版本的时机 |
| 8. 同步公开库源码 | AI | 把 `origin resource/**`、`source/desktop/**`、`source/package.json` 拷到公开库副本，见 §2 |
| 9. 两个仓库都 commit + push | AI | 收到第 6 步口令即视为**已授权推送**，不必再问 |

要点：

- **「改源码」指的是同步公开库那份源码副本**，不是回头再改开发目录的代码。开发目录的代码在第 1 步就改完了、也是第 3 步打包的来源。
- 第 4 步的等待是刻意的。测出问题就回第 1 步接着改，**不会在仓库里留下一版没验证过的提交**。
- 第 9 步是这条流程里唯一免问推送的场景。用户没说那句口令时，`git push` 仍然要先问（私有库带明文 API key）。
- 发 Release 是独立的一步，用户可能自己在 GUI 里做掉。动手前先 `git fetch` 看看 tag 在不在，别重复发。

### 2.2 没收到口令就不升版本号

**只有在用户说出「改源码提交」之后，才允许把 `source/package.json` 的 `version` 往上加。**
在那之前无论改多少东西、打多少次包，版本号都保持不动，后打的包直接覆盖 `source/release/` 里同名的那个。

因为 §2.1 那个循环可能转好几轮：出包 → 用户测 → 有问题 → 接着改 → 再出包。
每轮升一个号的话，`release/` 里会堆一串从来没发布过的版本，
而公开库 Release 只有真正发出去的那几个，两边很快就对不上，
日后排查「用户装的到底是哪一版」会非常痛苦。

具体做法：

- 每轮修改照常改代码、更文档、打包，**跳过升版本号**。
- 本篇 §3 的记录还是要写，挂在**当前这个版本号**下。同一个号下已经有一条记录了，
  就往那条里补内容，别新起一条——否则一个没发布过的版本会有好几条记录。
- 收到「改源码提交」后，在同步公开库之前先升一次版本、重新打包，再拿这个包发 Release。

> 例外：用户明确说了「升到 x.y.z」，按用户说的来。
>
> 这条规则从 1.2.19 开始执行（1.2.19 本身是最后一个按旧规矩自动升上来的号）。

### 2026-08-28 1.2.17：修「获取模型清单」被系统代理吞掉、展开 API 卡片不再跳回顶部

1.2.16 实测出的两个问题，都是老代码里就有、这次才暴露出来的。

**① 「获取模型清单 / 测试」报 `[WinError 10061] 目标计算机积极拒绝`**

- 改了什么：`backend/model_probe.py` 新增 `_opener()`，`_request()` 改用它，
  显式只吃环境变量里的代理（`ProxyHandler(getproxies_environment())`），
  不再读 Windows 注册表里的系统代理。
- 为什么：`model_probe` 用的是 `urllib.request.urlopen`，它在 Windows 上会把
  「Internet 选项」里那份系统代理算进来；而真正发对话请求的 `llm.py` 走
  openai/httpx，**httpx 只认 HTTP_PROXY / HTTPS_PROXY 环境变量，不读注册表**。
  测试机的注册表里挂着 `ProxyEnable=1` + `ProxyServer=127.0.0.1:80`（80 端口

  组合：**聊天正常，一点「获取模型清单」就失败**——同一个地址同一把密钥，

- 为什么：`userData` 是 `%LOCALAPPDATA%\AI Chatbot`，而多机同步的 junction 挂在它下面的 `data\` 子目录上，配置文件在根目录 = **在同步范围外**，换台电脑后设置里一个 API 都没有。另外旧版用 `safeStorage`（Windows 上是 DPAPI）加密 Key，密文绑定当前用户+当前机器，即使把文件拷过去也解不开，所以同步 Key 就只能存明文——绘图 API 的 Key 本来也是明文存在 `chatbot.db` 里的，这次是对齐而非降级。

  - 迁移只在跑新版本的机器上生效。还装着 1.2.7 的机器不会自动把 Key 迁出来。
