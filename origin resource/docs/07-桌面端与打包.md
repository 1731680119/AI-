# 桌面端与打包

Electron 外壳有约 2400 行脚本，业务文档基本不覆盖，这篇专门讲它。文件都在 `../source/desktop/`。

## 1. 三层结构与边界

```
主进程 main.cjs（Node 权限，能开进程、读文件、管窗口）
        ↕  只能通过 preload.cjs 暴露的方法通信
渲染进程（React 页面，contextIsolation 开启，拿不到 Node）
        ↑  did-finish-load 后注入
page-enhancements.js + enhancements.css（桌面端专属 UI）
```

规矩：页面**不能**直接 `require`，所有主进程能力必须在 `preload.cjs` 里显式挂到 `window.chatbotDesktop`。加桌面能力的顺序是「main.cjs 写 `ipcMain.handle` → preload.cjs 加一行 → 页面调用」，三处漏一处就静默失效。

## 2. 启动流程

`main.cjs` 的关键节点：

1. `app.setPath('userData', %LOCALAPPDATA%\AI Chatbot)`（`main.cjs:46`），**这是数据目录的根**，与后端 `paths.py` 的 `DATA_DIR` 必须一致。
2. `diag.init`（`:52`）把主进程日志写到 `data/logs`，和后端同一个目录，导出诊断包时三层日志才齐。
3. `requestSingleInstanceLock`（`:57`）单实例，第二次启动只开新窗口（`second-instance:1061`）。
4. `reservePort:306` 抢一个空闲端口 → `startBackend:362` 拉起后端 exe → `waitForBackend:327` 轮询等就绪。

   `waitForBackend` **不是单纯的定时超时**：后端是 PyInstaller 单文件 exe，刚升级后第一次跑要先把几十 MB 解到临时目录、还会被 Defender 整包扫一遍，冷启动几十秒很正常（原来写死 30 秒，被这个场景打穿过，见 05 §2）。现在只要 `backendProcess` 还活着就继续等，硬上限放到 5 分钟兜底；进程要是已经退了就立刻失败，把真实死因让给 `exit` 回调去报，不再盖成「超时」。等待超过 20 秒会写一条 `backend` 的 warn 日志，事后能分清是慢启动还是真卡死。
5. `createWindow:710` 开窗并 `loadURL(backendUrl)`；`did-finish-load` 时 `injectEnhancements:697` 注入脚本和样式。
6. 上次异常退出的话，`promptLastRunCrashed:988` 提示查看日志。

后端 stderr 的最后 40 行会被 `appendStderrTail:81` 留着，异常退出时随崩溃记录写下（`reportCrash:91`）。排查后端起不来先看这个。

## 3. 多 API 自动切换（改这块务必读完）

一个模型可以配多个 API 渠道，失败自动换下一个。逻辑跨主进程和注入脚本两侧：

- 配置存 `%LOCALAPPDATA%\AI Chatbot\desktop-settings.json`（`settingsPath:75`），结构见 `DEFAULT_ENHANCEMENTS:32`：`apiList`、`apiTimeoutSeconds`（默认 15 秒）、`modelApiMap`（模型 → 上次成功的渠道）、`deepseekUrl`、`prompts`。
- API Key 落盘前经 `encryptApiKey:141` 加密，读出走 `decryptApiKey:147`。**返回给页面的一律是 `publicEnhancementSettings:157` 的脱敏版**，只有用户点“显示”才走 `desktop:reveal-api-key`。加字段时不要顺手把明文 key 带出去。
- 尝试顺序由 `apiAttemptPlan:743` 决定：只取 `enabled` 的渠道，并把 `modelApiMap` 里缓存的那个轮到最前，所以常用渠道不会每次从头试。
- 单次尝试：`beginApiAttempt:778` 先拿全局串行锁（`acquireApiLock:758`，避免两个请求互相踩设置），再把该渠道的 `base_url`/`api_key` **临时写进后端设置**，返回一个 token；`finishApiAttempt:800` 用完把设置清空并放锁。45 秒兜底自动释放。
- 全部渠道失败时，`cleanupFailedAttempt:791` 直连 SQLite 把这轮产生的半截消息删掉并回退 `active_leaf_id`，避免会话里留下空消息。它用 `node:sqlite` 直接操作 `data/chatbot.db`，**改消息表结构时这里要同步改**。
- 页面侧的等待提示和失败重试对话框在 `page-enhancements.js`，通过 `chatbot-api-match-waiting`、`chatbot-api-match-complete`、`chatbot-api-failures` 三个自定义事件驱动。

## 4. 注入脚本

`page-enhancements.js` 往 React 页面里加桌面端才有的东西：

| 功能 | 位置 | 依赖的类名 |
| --- | --- | --- |
| 右键菜单（解释、找问题、优化代码） | `:221` | — |
| 全局提示 toast | `:229` | `.enh-toast` |
| 等待遮罩（切换 API、上传、生成图片、保存） | `:243`、`:280` | `.enh-waiting`、`.error-banner`、`.uploading-label`（**已失效，见下**）、`.image-submit`、`.modal-footer .btn-primary` |
| DeepSeek 标签栏 | `:327` | `.enh-tabbar` |
| API 全部失败的重试对话框 | `:381` | `.enh-failure-overlay`、`.send-btn` |
| 设置里的多 API 列表（拖拽排序、启停、显示 key） | `:422` 起 | `.enh-settings-slot`、`.modal .modal-body` |
| 接管设置保存按钮 | `:637` | `.modal-footer .btn-primary` |

**这是最脆的一层**：全靠 CSS 类名找位置。React 侧改结构类名，桌面端 UI 会无声消失，而且开发模式（浏览器里跑 Vite）看不出来，只有装成桌面版才暴露。改 React 结构后请对着上表检查一遍。注入样式的类名统一 `enh-` 前缀，别和业务样式混用。

### 已知失效：上传中的等待遮罩

`page-enhancements.js:282` 用 `document.querySelector('.uploading-label')` 判断是否正在上传，但 `Composer.tsx:301` 渲染那个「上传中…」标签时只写了内联 `style`，**没有 `uploading-label` 类名**，所以这个判断永远是 `false`，上传时的等待遮罩从来没生效过。

两种修法，任选一种（改完记得同步 08 的变更记录）：给 `Composer.tsx:301` 的 `<span>` 补上 `className="uploading-label"`，或把注入脚本的选择器改成实际存在的元素。前者更稳，因为注入脚本这层本来就依赖类名契约。

这正好是上面那条「靠类名定位」风险的实例：类名对不上时不报错，只是功能静静地不工作。

## 5. 窗口与托盘

- 关窗行为由 `closePreference` 控制，三个值 `ask` / `close` / `tray`（`VALID_CLOSE_PREFERENCES:27`），`askCloseAction:480` 弹选择框。
- 最小化到托盘 `minimizeWindowToTray:462`，恢复 `restoreWindow:454`，每个窗口一个托盘图标，关掉时 `destroyWindowTray:440`。
- 所有窗口关闭后不直接退出（`window-all-closed:1062` 是空的），而是 `scheduleShutdownIfEmpty:417` 延迟 `CLOSE_DELAY_MS`（5 秒）再退，期间新开窗会 `cancelScheduledShutdown:412` 取消。退出统一走 `exitApplication:424`，它负责 `stopBackend:397`。
- DeepSeek 内嵌标签页：`createDeepseekTab:618` 开 WebContentsView，`trySubmitDeepseekPrompt:566` 自动填提示词，标签栏高度常量 `DEEPSEEK_TAB_HEIGHT:26` 要和 `updateDeepseekBounds:519` 的布局对上。

## 6. 打包

配置在 `../source/package.json`，命令 `npm run dist`（`electron-builder --win nsis --x64`），产物落在 `../source/release/AI-Chatbot-Setup-<version>.exe`。

要点：

- `build.files` 只含 `desktop/**/*` 和 `package.json`。前端和后端是通过 `build.extraResources` 从 `source/frontend/`、`source/backend/` 拷进 `resources/` 的。**往 asar 里塞前端文件是错的方向。**
- `build.electronDist = "electron-dist"`，`asar: true`，NSIS 非一键安装（可改安装路径，`deleteAppDataOnUninstall: false`，所以升级不丢数据）。
- `allowScripts` 字段是有意加的（放开 electron 的 postinstall），**不要清掉**。
- 版本号只改 `source/package.json` 的 `version`，安装包文件名由 `artifactName` 自动带上。
- 完整流程：改 `origin resource/frontend/src` → `npm run build` → 把 `frontend/dist/` 同步到 `source/frontend/` → `cd source && npm run dist`。

验证改动是否真的进了包：grep `source/frontend/assets/*.css`（或 `*.js`）里的关键字符串，比重新装一遍快得多。

## 7. 打包环境的三个坑

**坑一：`ELECTRON_RUN_AS_NODE`**
VSCode 扩展宿主会传下这个环境变量，`electron.exe` 会退化成普通 Node，`require('electron')` 拿不到 API，表现为 `desktop/main.cjs` 报 `Cannot read properties of undefined (reading 'setPath')`。设成空字符串**无效**，必须彻底 `unset ELECTRON_RUN_AS_NODE`。

**坑二：electron 二进制没装好**
`source/node_modules/electron/dist/` 为空时报 `Electron failed to install correctly`。npm 的 allow-scripts 会拦 postinstall，extract-zip 也可能“成功”却什么都没解出来。手动修：从 `%LOCALAPPDATA%\electron\Cache\<hash>\electron-v<版本>-win32-x64.zip` 执行 `Expand-Archive -LiteralPath $zip -DestinationPath dist -Force`，再写 `node_modules/electron/path.txt`，内容一行 `electron.exe`。

**坑三：别用 `electron-dist` 调试**
它是改过名的精简发行版，没有 `default_app.asar`，`electron .` 起不来。本地跑应用只能用 `source/node_modules/electron` 那套。

## 8. 需要先问用户的操作

- 运行 `source/release/` 里的安装包（会覆盖当前已安装版本）。
- 删除或覆盖 `release/` 里的历史安装包。
- 改动已安装目录（`AI Chatbot.exe`、`*.dll`、`*.pak`、`locales/`、`resources/`）——那些是运行时产物，改了要重装才能恢复。
