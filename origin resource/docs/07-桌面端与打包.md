# 桌面端与打包

Electron 外壳有约 2400 行脚本，业务文档基本不覆盖，这篇专门讲它。文件都在 `../source/desktop/`。

## 1. 三层结构与边界

```
主进程 main.cjs（Node 权限，能开进程、读文件、管窗口）
        ↕  只能通过 preload.cjs 暴露的方法通信
渲染进程（React 页面，contextIsolation 开启，拿不到 Node）
        ↑  did-finish-load 后注入
page-enhancements.js + enhancements.css（桌面端专属 UI）
```

规矩：页面**不能**直接 `require`，所有主进程能力必须在 `preload.cjs` 里显式挂到 `window.chatbotDesktop`。加桌面能力的顺序是「main.cjs 写 `ipcMain.handle` → preload.cjs 加一行 → 页面调用」，三处漏一处就静默失效。

## 2. 启动流程

`main.cjs` 的关键节点：

1. `app.setPath('userData', %LOCALAPPDATA%\AI Chatbot)`（`main.cjs:49`），**这是数据目录的根**，与后端 `paths.py` 的 `DATA_DIR` 必须一致。
2. `diag.init`（`:54`）把主进程日志写到 `data/logs`，和后端同一个目录，导出诊断包时三层日志才齐。
3. `requestSingleInstanceLock`（`:59`）单实例，第二次启动只开新窗口（`second-instance:1193`）。
4. **`splash.create()` 先把启动画面开出来**（`splash.cjs`）。必须在 `startBackend()` 之前——
   后端冷启动几十秒，在它就绪前主窗口还没创建，屏幕上会一直空着，用户容易以为没启动成功而反复双击。
   它 `loadFile` 一个本地 html，**不走 `backendUrl`**（那时候后端还不存在）。
   各步骤之间用 `splash.setStatus()` 更新底部那行小字。
5. `reservePort:364` 抢一个空闲端口 → `startBackend:420` 拉起后端 exe → `waitForBackend:385` 轮询等就绪。

   `waitForBackend` **不是单纯的定时超时**：后端是 PyInstaller 单文件 exe，刚升级后第一次跑要先把几十 MB 解到临时目录、还会被 Defender 整包扫一遍，冷启动几十秒很正常（原来写死 30 秒，被这个场景打穿过，见 05 §2）。现在只要 `backendProcess` 还活着就继续等，硬上限放到 5 分钟兜底；进程要是已经退了就立刻失败，把真实死因让给 `exit` 回调去报，不再盖成「超时」。等待超过 20 秒会写一条 `backend` 的 warn 日志，事后能分清是慢启动还是真卡死。
6. `createWindow:768` 开窗并 `loadURL(backendUrl)`；`did-finish-load` 时 `injectEnhancements:755` 注入脚本和样式。
   `ready-to-show` 里 `window.show()` **之后**才 `splash.close()`——反过来桌面会空一帧，看着像闪了一下。
7. 上次异常退出的话，`promptLastRunCrashed:1063` **先把日志打包成诊断文件夹再弹窗**（见 §2.1）。
8. 启动收尾处 `archive.cleanup:1236` 清理过期诊断文件夹，每天最多跑一次。

启动画面还有三个**异常出口**也要收掉它（它是 `alwaysOnTop`，不收会压在对话框上面）：
启动失败的 `catch`、后端意外退出的 `showErrorBox` 之前，以及 `waitForBackend` 超 20 秒时
顺带 `setStatus` 补一句「首次启动需要解包」。`splash.close()` 是幂等的，多调无害。

后端 stderr 的最后 40 行会被 `appendStderrTail:90` 留着，异常退出时随崩溃记录写下（`reportCrash:100`）。排查后端起不来先看这个。

### 2.1 崩溃诊断文件夹（`diagnostics-archive.cjs`）

异常退出后下次启动，日志会被自动打包到：

```text
%LOCALAPPDATA%\AI Chatbot\data\logs\diagnostics\未处理-YYYY-MM-DD-HHMMSS\
```

**是文件夹，不是 zip**。内容：`环境信息.txt`（版本／系统／崩溃摘要，先看这个）、`说明.md`、以及从 `logDir` 顶层拷来的全部日志文件（`.clean-exit`、`.session` 这两个状态标记会跳过）。

几个刻意的设计，改之前先读：

- **不走后端 `/api/diagnostics/bundle`**。闪退时后端多半没起来，走后端等于什么都拿不到，所以桌面层直接 `copyFileSync`。别把这条依赖加回去。设置页那个「导出诊断包」按钮仍然走后端，是另一条路，两者不冲突。
- **先打包再弹窗**。`promptLastRunCrashed` 里 `createArchive` 在 `showMessageBox` 之前调用，用户点「忽略」日志也已经存好了。弹窗按钮是 `打开文件夹` / `标记为已处理` / `忽略`；打包失败时降级成 `打开日志文件夹` / `忽略`。
- **状态只看文件夹名前缀**（`未处理-` / `已处理-`）。程序改名和用户在资源管理器里手改都有效，不额外存状态文件。
- **保留天数按文件夹名里的时间算**，不看 mtime——拷贝、同步、杀毒软件都会改 mtime。`已处理` 超 30 天删，`未处理` 超 90 天删（未处理留久是防止用户还没看就被清掉）。
- **清理不用常驻定时器**，靠 `diagnostics/.last-cleanup` 里的日期判断同一天是否扫过。闪退频繁时定时器根本活不到触发。
- `createArchive` 内部吞掉所有异常，失败返回 `{ created: false, error }`。**它绝不能抛**——打包日志把启动流程带崩是最糟的结果。

> 给 AI 的规矩：靠某个 `未处理-…` 文件夹排查并修完问题后，自己把前缀改成「已处理」，不用等用户提醒。

## 3. 多 API 与模型切换（改这块务必读完）

**1.2.16 起改成了「渠道 → 模型」两级选择，不再自动切换渠道。** 每条渠道自带一份模型清单，用户在输入框的模型菜单里选的是「某渠道的某个模型」，选了谁就只调谁；它报什么错就原样呈现什么，不再轮询别家。这是为了修掉旧版的两个毛病：真实原因被「所有 API 均不可用」的汇总糊掉，以及串着等好几家让人误以为是超时。

- 配置存 `%LOCALAPPDATA%\AI Chatbot\data\desktop-settings.json`（`settingsPath:87`），结构见 `DEFAULT_ENHANCEMENTS:36`：`apiList`、`apiTimeoutSeconds`（默认 15 秒）、`deepseekUrl`、`prompts`、`legacy`。
  **注意是 `data\` 子目录，不是 `userData` 根目录**——`data\` 才是多机同步 junction 的挂载点，放根目录就同步不到（1.2.7 及更早就是放在根目录的，换台电脑后设置里一个 API 都没有）。
- `apiList` 里每条渠道多了 `models: [{ name, capability }]`，`capability` 取 `'chat'` 或 `'image'`。归一化在 `normalizeModelEntry:128` / `normalizeApiItem:136`，同一渠道内按 `capability::name` 去重。**`saveEnhancementSettings:285` 里前端没带 `models` 就沿用已存的那份**——别在保存别的字段时顺手把用户「获取模型清单」的结果清空。
- 旧版的 `modelApiMap`（模型 → 上次成功的渠道）已退役。`normalizeEnhancements:150` 把它备份进 `legacy` 再删掉，不直接扔，回退时还能捞。
- **API Key 明文落盘**，字段名就是 `apiKey`。旧版用 `safeStorage` 加密，但 Windows 上那是 DPAPI，密文绑定当前用户+当前机器，换台电脑解不开，跟多机同步冲突；绘图 API 的 Key 本来也是明文存在 `chatbot.db` 里的，这里是对齐。`migrateSettingsLocation:204` 负责把旧位置的配置搬过来并解密，旧文件改名 `.bak` 保留，挂在 `loadDesktopSettings()` **之前**。
  代价：`user-data/desktop-settings.json` 进 git 后，明文 Key 就在私有库历史里删不掉了。
- **返回给页面的一律是 `publicEnhancementSettings:254` 的脱敏版**——那句解构 `({ apiKey, ...item })` 是把明文 Key 挡在渲染进程外的唯一一道闸，只暴露 `hasKey`；只有用户点“显示”才走 `desktop:reveal-api-key`。加字段时不要顺手把明文 key 带出去。
- 渠道解析由 `apiAttemptPlan:864` 决定，**只返回一条**。优先级：前端在请求体里带的 `api_id` → 自己模型清单里声明了该模型的渠道 → 第一个启用的渠道。最后那条兜底是给迁移场景的（模型清单还是空的，这时候不该直接说「没有可用 API」）。
  > 已知缺口：前端**明确指定了 `api_id` 却没命中**（选完又把那条渠道删了/禁用了）时也会兜到 `enabled[0]`，等于静默改投别家。这跟「选了谁就只调谁」是矛盾的，等有人踩到再收紧。
- 单次尝试：`beginApiAttempt` 先拿全局串行锁（`acquireApiLock:849`，避免两个请求互相踩设置），再把该渠道的地址和密钥 **临时写进后端设置**，返回一个 token；`finishApiAttempt` 用完把设置清空并放锁。45 秒兜底自动释放。
  **1.2.19 起入参多了 `target`**（`'chat' | 'image'`，默认 chat）：`apiSettingsPatch(target, ...)` 决定写的是 `base_url`/`api_key` 还是 `image_base_url`/`image_api_key`，`finishApiAttempt` 按锁上记着的同一个 target 清空。图片渠道原来那份独立的 `image_providers` 配置已经删了，绘画和聊天现在共用「多 API」这一套。
- **旧版的 `cleanupFailedAttempt` 已整块删除。** 它当年直连 `node:sqlite` 把轮询中途产生的半截消息删掉再换下一家；现在只打一个渠道、失败就原样报错，没有要回滚的中间态了。**别再把 `node:sqlite` 直连加回来。**
- 页面侧的失败对话框在 `page-enhancements.js:346`，只由 `chatbot-api-failures` 一个自定义事件驱动。旧的 `chatbot-api-match-waiting` / `chatbot-api-match-complete` 随轮询一起去掉了，dispatch 和 listener 两边都已清干净。

### 3.1 渠道选择在前端怎么传下来

- 输入框的模型菜单：`frontend/src/hooks/useDesktopChannels.ts` 读渠道列表（顺带滤掉「没启用 / 没地址 / 没密钥」的），`groupByChannel()` 按 `capability` 摊成「渠道 → 模型」；`Composer.tsx` 桌面端走分组菜单，浏览器里没有这个桥就退回 `settings.models` 那份全局清单。菜单每次打开都重新拉一次，因为模型清单可能刚在设置页里改过。
- 选中结果分两半存：**模型名**进 `settings.default_model`（能跨重启），**渠道 id** 只放 store 里的 `chatApiId`（本次运行）。渠道 id 存不进后端设置——`SettingsPatch` 是 `extra="forbid"`，加字段要连着改后端和数据库。
  > 代价：重启后渠道选择丢失，退回「谁声明了这个模型就用谁」。两家渠道都声明同名模型时，落到的是靠前那家，不一定是你上次选的。真要修的话，渠道 id 本来就是桌面端概念，`desktop-settings.json` 才是它的家。
- 请求体里的 `api_id` 由注入层的 fetch 补丁读走。**1.2.19 起拦三条路径**：`POST /api/chat` 走 `runChatRequest`，`POST /api/images/generate` 和 `POST /api/images/edit` 走 `runImageRequest`（`target: 'image'`）。后者的 `imageRequestFields()` 同时认 JSON 体和 FormData——编辑接口是 multipart，`JSON.parse` 那条路走不通。后端自己用不上 `api_id`，但 `ChatBody` / `GenerateBody` / `/edit` 的表单都必须声明这个字段，否则将来给它加 `extra="forbid"` 会直接 422。
- 绘画页的模型选择框（`ImagePage.tsx`）和输入框那个是同一套：`useDesktopChannels` + `groupByChannel(channels, 'image')`。选中后**模型名**写进 `settings.image_model`（跨重启），**渠道 id** 只进 store 的 `imageApiId`（本次运行），和聊天那边的取舍一致。生成和编辑两个 tab 共用这一个选择器。

### 3.2 每条渠道的模型清单 UI

`buildModelBlock:662` 生成，挂在展开后的渠道卡片里，**只重绘自己这一小块**——整表重绘会把正在填的地址、密钥输入框全部重建，内容和光标位置都会丢。

- 「获取模型清单」→ `POST /api/settings/model-list`，只读清单不产生费用；勾选后按底部的「添加为：对话/绘画」批量加进来。
- 「测试」→ `POST /api/settings/model-test`，真发一次极短请求。凭据优先用输入框里刚填的，没填才去 `revealApiKey` 取已存的那把（`probeCredentials:636`）。
- 这两个探测都走 `originalFetch`，不经过 fetch 补丁。
- 后端侧这两条走 `model_probe._request`，它用的是**显式禁掉注册表代理**的 opener（1.2.17 起，见 05 §18）。别改回裸 `urllib.request.urlopen`——那会读 Windows 的系统代理，而发对话的 httpx 不读，结果就是「聊天正常、一点检测就 10061」。
- 勾选框的 `width` 要显式压回去：`shared-components.css` 里 `.field input` 的 `width:100%` **没排除 checkbox**，见 `enhancements.css` 的 `.enh-model-option input[type='checkbox']`。
  > 已知缺口：`renderPicker` 里判断「已在清单里」时把能力写死成 `'chat'`，底部能力下拉框改成「绘画」也不会重算勾选框状态。于是同一个模型没法通过选择器同时加成对话和绘画（手动添加后改行内的下拉框可以绕过）。

| 全局提示 toast | `:229` | `.enh-toast` |
| 等待遮罩（切换 API、上传、生成图片、保存） | `:243`、`:280` | `.enh-waiting`、`.error-banner`、`.uploading-label`（**已失效，见下**）、`.image-submit`、`.modal-footer .btn-primary` |

### 4.1 拖动排序（1.2.14 起改用指针事件）

**实现有两份，逻辑等价，改效果时要一起改**：

| 位置 | 用在哪 |
| --- | --- |
| `page-enhancements.js` 的 `makeSortable()` | 注入的「多 API」卡片列表（vanilla DOM，跑在 React 之外） |
| `frontend/src/hooks/useSortableList.ts` | 输入框上方的模型菜单（顺序写回 `settings.models`）、设置页图片栏的多渠道列表（顺序即故障转移顺序，1.2.15） |

为什么不用 HTML5 drag&drop：它的拖影是浏览器截的静态位图，改不了大小和透明度，
也没法让下面的项目实时让位。要「缩小半透明跟随鼠标 + 原位留占位框 + 相邻项被顶开」
这套效果只能自己接指针事件。1.2.13 及更早用的是 drag&drop，1.2.14 整体换掉。

交互约定与踩过的坑：

- **中线判定用进入拖动时快照的原始位置**（`baseTop`），不是实时的 `getBoundingClientRect()`——
  后者已经被让位的 transform 改过了，拿它算会来回抖。
- **ghost 必须挂 `document.body`**。菜单和列表都可能有 overflow 裁剪，留在容器里拖出边界就没了。
  它是 `position: fixed`，z-index 要压过 `.model-menu` 的 40。
- **指针移动超过 `DRAG_THRESHOLD`（4px）才真正起拖**，否则「想点一下」会被判成拖动。
- 多 API 卡片和图片渠道卡片只认**手柄**（分别是 `.enh-drag-handle` / `.provider-drag-handle`）
  上按下，否则卡片里的输入框没法选中文本。React 侧靠 `useSortableList` 的第三个参数
  `handleSelector`（1.2.15 加的），和 `makeSortable` 的同名选项行为一致；
  两边都把这个判断放在 `preventDefault()` **之前**，否则输入框会点不进去。
  模型菜单整项都能拖，所以要靠 `onClickCapture` 挡掉拖动结束后浏览器补的那次 click，
  不然松手会顺带选中模型并关掉菜单。
- 三个状态类名：`.enh-sort-ghost` / `.enh-sort-placeholder` / `.enh-sort-shifting`
  （React 侧对应 `.sortable-*`）。被拖的那项**不加过渡**，否则松手回位时会多滑一下。

边缘自动滚动（1.2.13 加的）保留，只是触发事件从 `dragover` 换成了 `pointermove`：

- 手感由三个常量决定：`DRAG_SCROLL_ZONE`（触发区 60px）、`DRAG_SCROLL_MIN_SPEED`（2 px/帧）、
  `DRAG_SCROLL_MAX_SPEED`（18 px/帧）。要调只改这三个数，逻辑不用动。
- 滚动目标是**运行时**用 `scrollableAncestor()` 从 `.enh-api-list` 往上找的，当前命中
  设置弹窗的 `.modal-body`。所以这条不依赖固定类名。

### 已知失效：上传中的等待遮罩

`page-enhancements.js:282` 用 `document.querySelector('.uploading-label')` 判断是否正在上传，但 `Composer.tsx:418` 渲染那个「上传中…」标签时只写了内联 `style`，**没有 `uploading-label` 类名**，所以这个判断永远是 `false`，上传时的等待遮罩从来没生效过。

两种修法，任选一种（改完记得同步 08 的变更记录）：给 `Composer.tsx:418` 的 `<span>` 补上 `className="uploading-label"`，或把注入脚本的选择器改成实际存在的元素。前者更稳，因为注入脚本这层本来就依赖类名契约。

这正好是上面那条「靠类名定位」风险的实例：类名对不上时不报错，只是功能静静地不工作。

### 4.2 API 卡片折叠（1.2.15 起）

`renderApiList()` 默认只渲染标题行（`.enh-drag-handle` + `.enh-api-name` + `.enh-api-toggle`），点右侧的 ▾ 才把启用勾选、删除按钮和地址/密钥字段追加进来。要点：

- 展开状态存在 `injectSettings` 闭包里的 `expandedIds`（`Set`），**故意不持久化**：设置弹窗每次打开都会重新注入，于是一律从全部折叠开始。
- **重绘一律走 `renderApiListKeepingScroll()`，不要直接调 `renderApiList()`**（1.2.17 起）。后者是整表 `replaceChildren`，子节点一清空滚动容器的 `scrollHeight` 就归零，浏览器把 `scrollTop` 夹到 0——表现是点一下 ▾ 展开、整个设置弹窗弹回最顶上，卡片一多每次都要重新滚下来找。包装函数在重绘前后记录并还原滚动位置；滚的是 `scrollableAncestor(list)` 运行时找到的祖先（当前是 `.modal-body`），**没有写死类名**。展开/收起、删除、拖动排序、添加 API 四处都改用它了。
- 折叠再展开会**重建**输入框，所以 Key 输入框要把 `api.apiKey`（改了还没保存的值）填回去，否则用户填完一收一展就白填了。
- 新点「添加 API」的那条自动加进 `expandedIds`，不然按钮看起来像没反应。
- 前端设置页的图片渠道卡片是同一套观感，但那边是 React（`.provider-*` 类名，样式在 `styles/shared-components.css`），**改观感要两处一起改**。

### 4.2-b 卡片里的长文本（1.2.18 起）

上游的报错原文可能有好几百字（实测 grok-4.5 那次「测试」回的是 HTTP 503 加一整段报文），
不封宽度就会把整张 API 卡片横着撑到屏幕外。两头都得治，缺一条都不管用：

- **容器**：`.enh-api-list`、`.enh-api-card`、`.enh-model-block`、`.enh-model-rows` 四个
  `display: grid` 的容器都要写 `grid-template-columns: minmax(0, 1fr)`。grid 的默认列宽是
  `auto`（≈`max-content`），漏掉这条，列宽会跟着最长的那行内容走，子元素上的
  `overflow: hidden` 完全不起作用。**以后在这里加新的 grid 容器，照抄这条。**
- **弹性项**：`.enh-model-status` 用 `flex: 0 1 auto` + `min-width: 0`。原来写的是
  `flex: none` 配 `max-width: 40%`，看着像有上限其实两条都是摆设——`none` 不允许收缩，
  而百分比是相对已经被撑宽的行算的。`.enh-model-row` 也要 `min-width: 0`。
- **文本本身**：模型行的状态格**一律走 `setStatus(node, text)`**（`page-enhancements.js:664`），
  它把文字压成单行、截到 60 字，完整原文放进 `title` 供悬停查看。别再直接写 `textContent`。
- 同一段 message 也会经 `showToast` 显示，所以 `.enh-toast` 一并加了
  `max-width: min(520px, 88vw)` 和 `overflow-wrap: anywhere`。

## 5. 窗口与托盘

- 关窗行为由 `closePreference` 控制，三个值 `ask` / `close` / `tray`（`VALID_CLOSE_PREFERENCES:29`），`askCloseAction:562` 弹选择框。
- 最小化到托盘 `minimizeWindowToTray:544`，恢复 `restoreWindow:536`，每个窗口一个托盘图标，关掉时 `destroyWindowTray:522`。
- 所有窗口关闭后不直接退出（`window-all-closed:1194` 是空的），而是 `scheduleShutdownIfEmpty:499` 延迟 `CLOSE_DELAY_MS`（5 秒）再退，期间新开窗会 `cancelScheduledShutdown:494` 取消。退出统一走 `exitApplication:506`，它负责 `stopBackend:479`。
- DeepSeek 内嵌标签页：`createDeepseekTab:700` 开 WebContentsView，`trySubmitDeepseekPrompt:648` 自动填提示词，标签栏高度常量 `DEEPSEEK_TAB_HEIGHT:28` 要和 `updateDeepseekBounds:601` 的布局对上。

### 5.0 设置没保存时先问一句（1.2.19 起，1.2.21 补上「多 API」栏）

设置弹窗自己的叉/取消/点遮罩，走前端的 `requestClose()` 就够了。**主窗口的叉不行**——
「保存并关闭」需要 `draft` 和 `saveSettings()`，这两样都在渲染进程里，主进程拿不到，
所以原生 `dialog` 只能问「关不关」，问不了「要不要先存」。

做法是把决定权交回页面：主进程只负责**拦住**这次关闭，把问题转发下去，然后等答复。

| IPC | 方向 | 作用 |
| --- | --- | --- |
| `desktop:set-settings-dirty` | 页面 → 主进程 | 报告「设置弹窗里有没有未保存改动」，主进程按窗口 id 存进 `settingsDirtyWindows` |
| `desktop:close-requested` | 主进程 → 页面 | 关窗被拦下了，请页面弹「保存 / 不保存 / 取消」 |
| `desktop:resolve-close` | 页面 → 主进程 | 答复 `'proceed'`（继续关）或 `'cancel'`（留下） |

`handleWindowClose` 里这段在 `closePreference` 判断**之前**：脏就 `preventDefault()` +
发 `desktop:close-requested`，不脏才照常走托盘/关闭/询问。收到 `'proceed'` 后**接着跑原来那套**
`closePreference` 逻辑——「数据要不要留」和「窗口去哪」是两个问题，故意不合并成一个弹窗。

**这里最大的风险是脏标记卡住、窗口再也关不掉**，所以清标记的地方有四处，改动时别删：

1. 前端的 `dirty` 是 `settingsOpen && (isDirty(draft, settings) || extrasDirty)` 算出来的，弹窗一关就自动报 false；
2. `SettingsModal` 卸载时的 cleanup 再报一次 false；
3. `did-finish-load` 里清 `settingsDirtyWindows` / `pendingCloseWindows`——页面一刷新渲染进程 state 全没了，
   标记不跟着清就永远为真；
4. `handleWindowClose` 兜底：已经问过一次还没答复，第二次点叉直接放行。

`isDirty()` 用 `JSON.stringify` 整体比，不逐字段比：`Settings` 三十多个字段、还有几个对象数组，
手写比较函数每加一个设置项就得记得改一处，漏了就是「改了却不提示」——正是这个功能要修的毛病。

**`isDirty()` 只看得见 React 那份 draft。**「多 API」栏是 `page-enhancements.js` 用原生 DOM
注入的，改动落在 `injectSettings()` 自己的闭包里，`settings` 从头到尾不变——1.2.19 那版因此
在这一栏完全不提示，改完直接关窗静默丢弃。1.2.21 补了一条通道：

- 注入层维护 `baseline` / `syncDirty()`，状态翻转时 `window.dispatchEvent` 一个
  `chatbot-settings-extras-dirty` 事件（`detail` 就是新的 dirty）；
- 同时把 `{ isDirty, save }` 挂到 `window.chatbotSettingsExtras`。
  **不能挂在 `chatbotDesktop` 上**——那是 contextBridge 暴露的冻结对象，加不了字段；
- 弹窗监听事件算进 `extrasDirty`，并在 `save()` 里先 `await settingsExtras().save?.()`。

**注入层原来那套「劫持底部保存按钮 click」的写法必须留在历史里，别改回去**：确认框里的
「保存」走的是弹窗自己的 `save()`，绕过按钮，只要保存动作还挂在按钮上，那条路就只存普通设置、
照样把 API 改动丢掉。现在按钮和确认框都只走 `save()` 这一个入口。

另外，点「显示」把已存的 Key 回填进输入框**不算改动**，靠 `revealedKeys` 记下回填值、比对时
归一成空串——漏了这层，点一下「显示」就被判成脏。

### 5.1 自动更新（1.2.12 起，`updater.cjs`；1.2.14 加了通道降级）

用 `electron-updater` + GitHub Release。主进程侧全在 `../source/desktop/updater.cjs`，渲染侧是
`frontend/src/hooks/useUpdateState.ts` + `features/settings/components/UpdatePanel.tsx`
（设置弹窗的「关于与更新」一栏）。

流程：`main.cjs` 在 `createWindow()` 之后调 `updater.init(broadcastUpdateState, () => enhancements.updateProxy)`
（第二个参数是个 getter，取用户在设置里手填的代理地址，**不能在 init 时取值**——那会锁死成启动时的旧值）→
延迟 `FIRST_CHECK_DELAY_MS`（8 秒，让后端和窗口先就绪）静默查一次 → 状态通过
`desktop:update-state` 广播给所有窗口 → 有新版时侧边栏「设置」按钮和该栏目上出现红点
（`.nav-dot`）。**不弹窗**，下载和安装都要用户在面板里手动点。

**自动检查一辈子只有这一次**（1.2.14 改的）：`check(manual)` 开头用模块级的 `autoCheckDone`
挡住后续所有非手动调用，也没有任何轮询定时器。之后要查只能靠用户点「检查更新」。

IPC 四个（`registerIpc:187`，`preload.cjs` 里对应 `getUpdateState` / `checkForUpdate` /
`downloadUpdate` / `installUpdate` / `onUpdateState`）：

| 通道 | 作用 |
| --- | --- |
| `desktop:update-state` | 双向：渲染进程 `invoke` 拉当前状态；主进程 `send` 广播变化 |
| `desktop:update-check` | 手动检查。手动失败会把错误抛给界面，后台检查只写日志 |
| `desktop:update-download` | 下载（`autoDownload = false`，不会自作主张下） |
| `desktop:update-install` | 退出并安装 |

改这块前必须知道的几条：

- **`autoDownload = false` + `autoInstallOnAppQuit = false`** 是刻意的。用户装的是非一键安装器，
  自动下好、退出时偷偷装，会让人莫名其妙看到安装向导。
- **`quitAndInstall(false, true)`——非静默**。静默安装会忽略用户自定义的安装目录，
  可能在默认路径装出第二份。所以点「退出并安装」后会正常走 NSIS 向导。
- **`prepareQuitForUpdate()` 只置 `isQuitting = true` 并 `cancelScheduledShutdown()`**，
  故意不做 `stopBackend` / `markCleanExit`——那两件事仍由既有的 `before-quit` 做，且只做一次。
  漏掉 clean-exit 标记的话，下次启动会把这次更新误判成崩溃，生成一个假的「未处理-」诊断文件夹
  （§2.1），把真崩溃记录淹掉。
- **`require('electron-updater')` 包在 try/catch 里**，依赖缺失时状态变 `disabled`，
  不能让主进程起不来。`!app.isPackaged` 时也直接 `disabled`——开发模式没有 `app-update.yml`。
- Release 正文在面板里按**纯文本**渲染（`<pre>`），不引 Markdown 渲染器：那是从网络拿来的内容。

#### 连不上时的通道降级（1.2.14，`net-fallback.cjs`）

`check()` 和 `download()` 各自先 `openChannel()`：调 `netFallback.establish()` 依次试
**直连 → DoH 解析直连 → 镜像站 → HTTP 代理**，第一个通的那条拿来
`autoUpdater.setFeedURL({ provider: 'generic', url: channel.base })`，同时把线路描述写进
`state.channel` 显示给用户。

- **必须是 `generic` 而不是 `github` provider**：github provider 会自己拼 `api.github.com`
  的地址，镜像站就白设了。
- **`finally` 里一定要 `netFallback.teardown()`**，成功失败都要。`quitAndInstall()` 里也兜了一次。
  这就是需求里说的「下载完成后关闭代理」。
- 用户手填的代理在设置 → 多 API 那一栏的「更新代理（可选）」，存在
  `desktop-settings.json` 的 `enhancements.updateProxy`，留空就自动探测系统代理。
- **刻意不接 Steamcommunity_302**：它要 WinDivert 内核驱动 + 管理员权限，非正常退出会把劫持
  规则留在系统里，下次开机整机断网。本模块的改动全在本进程内存（自定义 `lookup` / 自定义 Agent），
  不写 hosts、不装驱动、不改系统代理、不起子进程，进程一死就没了。**这条不要改。**

### 5.2 导出图片的原生保存对话框（`desktop:save-binary`）

图片导出（04 §2「图片」）拿到二进制后，走 `desktop:save-binary` 让主进程弹
`dialog.showSaveDialog` 再 `fs.writeFileSync`。**不能只靠 `<a download>`**——Electron 里它
一般直接丢进下载目录不弹窗，达不到「选保存位置」的效果。没有桥（浏览器里跑）时前端才回退到
`<a download>`。

## 6. 打包

配置在 `../source/package.json`，命令 `npm run dist`（`electron-builder --win nsis --x64 --publish never`），产物落在 `../source/release/`：`AI-Chatbot-Setup-<version>.exe` 和 `latest.yml`。

要点：

- **`latest.yml` 必须和 exe 一起上传到 GitHub Release**，否则所有客户端都检测不到更新，
  而且**不会报错**——`autoUpdater` 只是安静地拿到 404。这是 1.2.12 起最容易漏的一步。

  ```bat
  gh release create v<版本> ^
    "important resource\source\release\AI-Chatbot-Setup-<版本>.exe" ^
    "important resource\source\release\latest.yml" ^
    --repo 1731680119/AI- --title "v<版本>" --notes "变更说明"
  ```

  `--repo 1731680119/AI-` 不能省，在开发目录下跑 `gh` 默认会发到私有库 `ai-bot`。
- `build.publish`（github / owner `1731680119` / repo `AI-` / `releaseType: release`）是
  `resources/app-update.yml` 的唯一来源，**删掉它打出来的包就永远查不到更新**。
  打完包可以 grep `release/win-unpacked/resources/app-update.yml` 确认。
  `dist` 脚本带 `--publish never`，避免 electron-builder 自己往 GitHub 传东西。
- `nsis.differentialPackage: false` 是刻意的：开着会多产出一个 `.blockmap`，Release 变三个文件，
  漏传一个又是静默失效。关掉后每次只需上传两个文件。
- **老版本客户端收不到更新**。1.2.11 及更早里根本没有检查更新的代码，1.2.12 这一版仍需手动分发，
  自动更新从 1.2.13 起才真正生效。
- `build.files` 只含 `desktop/**/*` 和 `package.json`。前端和后端是通过 `build.extraResources` 从 `source/frontend/`、`source/backend/` 拷进 `resources/` 的。**往 asar 里塞前端文件是错的方向。**
- `electron-updater` 必须待在 `dependencies` 而不是 `devDependencies`——electron-builder 只把
  `dependencies` 打进 asar，放错地方就是运行时 `Cannot find module`。验证：
  `npx asar list release/win-unpacked/resources/app.asar | grep electron-updater` 应该有几十条。
- `build.electronDist = "electron-dist"`，`asar: true`，NSIS 非一键安装（可改安装路径，`deleteAppDataOnUninstall: false`，所以升级不丢数据）。
- `allowScripts` 字段是有意加的（放开 electron 的 postinstall），**不要清掉**。
- 版本号只改 `source/package.json` 的 `version`，安装包文件名由 `artifactName` 自动带上。
- 完整流程：改 `origin resource/frontend/src` → `npm run build` → 把 `frontend/dist/` 同步到 `source/frontend/` → `cd source && npm run dist`。
  **只改了 `source/desktop/**` 的话不用碰前端**，直接 `npm run dist` 即可。

验证改动是否真的进了包：

- 前端改动：grep `source/frontend/assets/*.css`（或 `*.js`）里的关键字符串。
- 桌面端改动：grep `source/release/win-unpacked/resources/app.asar`（`grep -a -F "函数名" app.asar`）。asar 是二进制但里面的源码是明文，能直接搜到；**顺便搜一下被删掉的旧符号，确认它归零**，比只确认新符号存在更能说明问题。

两种都比重新装一遍快得多。

## 7. 打包环境的五个坑

前三个是老坑，后两个是 2026-08-18 在一台**全新机器**上第一次打包时踩到的——`node_modules/`、`electron-dist/`、`release/` 全在 `.gitignore` 里，所以 clone 出来的仓库**没有任何打包环境**，得先搭。

**坑一：`ELECTRON_RUN_AS_NODE`**
VSCode 扩展宿主会传下这个环境变量，`electron.exe` 会退化成普通 Node，`require('electron')` 拿不到 API，表现为 `desktop/main.cjs` 报 `Cannot read properties of undefined (reading 'setPath')`。设成空字符串**无效**，必须彻底 `unset ELECTRON_RUN_AS_NODE`。

**坑二：electron 二进制没装好**
`source/node_modules/electron/dist/` 为空时报 `Electron failed to install correctly`。npm 的 allow-scripts 会拦 postinstall，extract-zip 也可能“成功”却什么都没解出来。手动修：从 `%LOCALAPPDATA%\electron\Cache\<hash>\electron-v<版本>-win32-x64.zip` 执行 `Expand-Archive -LiteralPath $zip -DestinationPath dist -Force`，再写 `node_modules/electron/path.txt`，内容一行 `electron.exe`。

**坑三：别用 `electron-dist` 调试**
它是改过名的精简发行版，没有 `default_app.asar`，`electron .` 起不来。本地跑应用只能用 `source/node_modules/electron` 那套。

**坑四：`npm install` 报 `UNABLE_TO_VERIFY_LEAF_SIGNATURE`**

```text
npm error request to https://codeload.github.com/electron/node-gyp/tar.gz/... failed,
npm error reason: unable to verify the first certificate
```

卡在 `electron/node-gyp` 这个 git 依赖上。Node 自带的证书库里没有本机网络链路上那张根证书（TLS 拦截、企业代理都会这样）。解法是让 Node 走 **系统证书库**：

```bash
NODE_OPTIONS=--use-system-ca npm install
NODE_OPTIONS=--use-system-ca npm run dist   # dist 也要，它得下 winCodeSign / nsis 二进制
```

**不要用 `npm config set strict-ssl false` 或 `NODE_TLS_REJECT_UNAUTHORIZED=0`**——那是把 TLS 校验整个关掉；`--use-system-ca` 是改走系统信任链，校验仍在。

**坑五：新机器上 `electron-dist/` 不存在，打包直接失败**

`build.electronDist = "electron-dist"` 要求这个目录存在，而它被 `.gitignore:8` 排除，只存在于已配置过的机器上。新机器要自己造一份（它是 electron 官方发行版减掉 `default_app.asar`）：

```bash
cd "important resource/source"
cp -r node_modules/electron/dist electron-dist
rm -f electron-dist/resources/default_app.asar
```

版本由 `devDependencies` 里的 `electron` 锁定，所以各机器造出来的是同一个发行版，**不会互相冲突**——`electron-dist/` 进不了 git，两台机器各持一份纯本地副本。

> §1 说的 `electron-dist/`「禁止改动」针对的是**已存在**的那一份，不是禁止在新机器上创建。分辨方法：`ls electron-dist` 报 no such file 就是新机器，可以建；已经有了就别碰。

## 8. 需要先问用户的操作

- 运行 `source/release/` 里的安装包（会覆盖当前已安装版本）。
- 删除或覆盖 `release/` 里的历史安装包。
- 改动已安装目录（`AI Chatbot.exe`、`*.dll`、`*.pak`、`locales/`、`resources/`）——那些是运行时产物，改了要重装才能恢复。
